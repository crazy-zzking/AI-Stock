## 二、Phase 0 — 统一回测引擎抽象（P0 · #1）

> 这是后续所有改造的地基。两个 `BacktestConfig` 同名异义、两个报告模型字段不兼容，每加一个功能要做两遍。

### 0.1 合并 BacktestConfig

**现状**：
- `AIStock.Core.Interfaces.BacktestConfig` — Strategy 引擎用（InitialCapital / Commission / MaxPositionPercent …）
- `AIStock.Selection.Backtest.BacktestConfig` — Selection 引擎用（HoldDays / Entry / StopLossPct …）

**方案**：合并为一个 `BacktestConfig`，放在 `AIStock.Core.Models`，包含两者全部字段：

```csharp

    public List<ExitRule> ExitRules { get; set; } = new();
    public List<EntryRule> EntryRules { get; set; } = new();

    // === Strategy 引擎字段 ===
    public decimal InitialCapital { get; set; } = 1_000_000m;
    public decimal CommissionRate { get; set; } = 0.03m;
    public decimal Slippage { get; set; } = 0.1m;
    public decimal StampTaxRate { get; set; } = 0.1m;
    public decimal ImpactCost { get; set; } = 0.05m;
    public decimal MaxPositionPercent { get; set; } = 10m;
```

### 1.2 修正 Sharpe Ratio 计算

**文件**: 同上，`CalculateSharpeRatio` 方法

**修复**: 从"逐笔收益 × √252"改为"逐日净值 → 日收益率 → mean/std × √252"。

### 1.3 修正 MaxDrawdown 计算

**文件**: 同上，`CalculateMaxDrawdown` 方法

**修复**: 从"逐笔平仓后算一次"改为"逐日 Mark-to-Market 计总权益"。

### 1.4 回测使用确定性信号

**文件**: 同上，`RunBacktestAsync` 方法

**修复**: `strategy.GenerateSignalAsync` 替换为确定性信号生成函数，或预计算信号后跑引擎。

### 1.5 事件数据覆盖不足告警（#8）

**文件**: `AIStock.Selection/Backtest/ReplayBacktestService.cs`

**问题**: `EventRecord` 表的历史深度仅从 05-30 起。回放区间更早时消息面特征为空，会系统性低估消息催化策略的绩效。

**修复**:
- `BacktestReport.Warnings` 新增一条：`"消息面数据仅覆盖 {NewsCoverageStart} 之后，此前回测不含消息因子"`
- `BacktestReport.NewsCoverageStart` 设为 `EventRecord` 表最早日期
- 前端 `BacktestReportView` 顶部黄条提示

### 1.6 市值/PE 为 0 静默失败告警（#9）

**文件**: `AIStock.Selection/Backtest/SnapshotRebuilder.cs`

**问题**: `TotalMarketCap = 0m` / `PeTtm = 0m`。若策略配置了 `MinMarketCap > 0`，回放模式下所有股票被过滤（0 < 阈值），导致零信号静默失败。

**修复**:
- `BacktestReport.Warnings` 新增一条：`"回放快照无历史市值/PE数据，市值筛选已自动跳过"`（仅当 `criteria` 中设了市值阈值且引擎检测到为回放模式时）
- `BacktestReport.MarketCapAvailable = false`（回放模式）
- `ReplayBacktestService` 在 `BacktestParamsAsync` 返回前将 Warnings 写入 report

### 3.4 改造 BacktestEngine.Run()

**文件**: `AIStock.Selection/Backtest/BacktestEngine.cs`

核心改动：把原来的硬编码止损/止盈判断替换为规则引擎遍历：

```csharp
// 原来
if (config.StopLossPct > 0 && bar.Low <= stopPrice) { ... }
if (config.TakeProfitPct > 0 && bar.High >= tpPrice) { ... }

// 改为
var rules = ResolveExitRules(config);  // 兼容旧的 StopLossPct + 新的 ExitRules
for (var i = entryIdx; i <= maxExitIdx; i++)
{
    var ctx = BuildExitContext(...);
    foreach (var rule in rules.OrderBy(r => r.Priority))
    {
        var result = rule.Evaluator(ctx);
        if (result != null) { exitIdx = i; exitPrice = result.ExitPrice; exitReason = result.Reason; goto done; }
    }
}
done:
```

`ResolveExitRules` 的兼容逻辑：
- 如果 `ExitRules` 非空 → 直接用
- 如果 `ExitRules` 为空但 `StopLossPct > 0 || TakeProfitPct > 0` → 从旧字段构造（向后兼容）
- 否则只保留 TimeExit(HoldDays)

## 七、Phase 5 — 回放回测性能优化（P2 · #7）

### 5.1 快照缓存

**文件**: `AIStock.Selection/Backtest/ReplayBacktestService.cs`

**问题**: 每次回放都从 kline_data 全量拉取所有股票的所有日 K，然后在内存中逐股重建快照。同一区间多次跑（如调参对比），重建重复执行。

**修复**:
- 引入内存缓存 `ConcurrentDictionary<(DateTime, string), DailyMarketSnapshotEntity>`，key = (日期, 代码)
- 同一次 `BacktestParamsAsync` 调用内共享（不跨请求，避免内存膨胀）
- `RebuildAllSnapshotsAsync` 先查缓存，未命中再计算

### 5.2 K 线查询瘦身

**问题**: `RebuildAllSnapshotsAsync` 拉 `klineBufStart` 到 `to` 的全市场 K 线，即使回放只涉及部分交易日。

**修复**:
- 先用 `SELECT DISTINCT Code FROM kline_data WHERE DateTime BETWEEN since AND to` 做代码预筛
- 已经过滤掉指数 secid ✅，但可以进一步：如果回放区间只有 30 个交易日，不需要拉 `since-90` 之前的数据做重建（除非刚上市的新股）。对大多数股票，`since-21` 的缓冲就够了。
- `raw.Where(k => !indexSecids.Contains(k.Code))` 改为在 SQL 层过滤：`.Where(k => !indexSecids.Contains(k.Code))` 已经在前 ✅

**改动量**：~30 行，主要是缓存逻辑。

### 5.3 并行重建

**修复**: `foreach (var g in raw.GroupBy(k => k.Code))` 改为 `Parallel.ForEach`，利用多核加速快照重建。

**注意**: `IFeatureCalculator` 需要线程安全（当前未验证）；如果不安全，加 `lock` 或串行执行 `CalculateAll`。

1. **不影响现有功能**：`BacktestConfig` 保留旧字段 `StopLossPct` / `TakeProfitPct`，标记 `[Obsolete]` 但继续工作。`BacktestEngine.Run()` 内部优先读 `ExitRules`，为空时从旧字段构造。

2. **API 完全向后兼容**：现有 GET/POST 参数不变，仅新增可选 `exitRules` 字段。前端默认不使用高级面板，显示效果与现在一致。

3. **发布顺序**：Phase 0（引擎统一）→ Phase 1（Bug 修复 + 告警）→ 上生产 → Phase 2（规则引擎）feature 分支验证 → Phase 3/4/5/6 按节奏推进。
